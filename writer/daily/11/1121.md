# 六大常见 Workflow 模式

## 模式一：顺序链（Sequential Chain）
最基础的模式，步骤 A → B → C 线性执行，上一步输出是下一步输入。

> 适用场景：文档处理流水线、内容生成、数据转换

## 模式二：条件路由（Conditional Routing）
根据某一步的输出内容，动态选择不同的后续路径。（意图分类）

> 适用场景：智能客服、多功能助手、问题分类处理

## 模式三：并行执行（Parallel Execution）
多个子任务同时运行，最后汇总结果。

> 适用场景：多维度分析、批量处理、独立子任务

## 模式四：ReAct 循环（Reason + Act）
AI 先推理决定做什么，再行动调用工具，根据结果继续推理，循环直到任务完成。这是 AI Agent 的核心模式。

让 AI 在思考和行动之间循环，直到完成任务。

> 适用场景	AI Agent、复杂任务执行、开放式问题求解

## 模式五：Plan & Execute（规划后执行）
先让 LLM 制定完整计划，再按计划逐步执行。与 ReAct 的区别是"先想清楚，再行动"。

## 模式六：多智能体协作（Multi-Agent）
多个专职 Agent 分工合作，每个 Agent 有自己的角色和工具集。

# DeepAgent 与 LangChain、LangGraph 的关系

| 框架 | 层级定位 | 核心职责 | 适用场景 |
|---|---|---|---|
| LangChain | 基础组件层 | 提供 Model、Prompt、Tool、Retriever、Output Parser 等 AI 基础组件 | 构建单个 Agent 或 AI 应用的基础能力 |
| LangGraph | 运行时层 | 提供状态管理、工作流编排、节点与边、Checkpoint 持久化能力 | 需要自定义图结构和执行流程的复杂场景 |
| Deep Agents | 应用框架层 | 在 LangGraph 之上封装规划、文件系统、子 Agent、记忆、上下文压缩等生产级能力 | 快速构建复杂多步骤 Agent，无需从头设计架构 |

> 三者并非相互替代，而是可以协同使用：LangChain 提供积木，LangGraph 是组织积木的工程框架，Deep Agents 是在此之上开箱即用的高级应用层。任何一个 LangGraph CompiledStateGraph 都可以作为 subagent 传入 Deep Agents，三层可以灵活混用。

# 传统 RAG 的局限
传统 RAG（Baseline RAG）的工作流程是：将文档切成小块 → 生成向量 → 问题来了时用向量相似度检索最相关的几块 → 送给模型生成答案。

这个方案对"精确检索"类问题效果不错，但在两类场景下表现较差：

- 跨文档关联推理：当答案需要把分散在不同文档里的信息串联起来时，向量相似度无法表达这种"关系"。例如"A 公司的 CEO 和 B 公司的创始人有什么交集？"
- 全局性摘要问题：当问题要求对整个语料库做宏观总结时，几块文本片段根本无法覆盖全貌。例如"这批财报文件里最核心的风险点是什么？"

# Harness Engineering（驾驭工程）

AI 模型已经能写出 100 万行代码。真正的挑战不再是让它写得更好，而是怎么驾驭它**稳定、可靠、不失控地**工作。

**Agent 的每一次失败，都是环境设计不完善的信号**。正确的回应不是换一个更强的模型，而是重新设计它运行的环境。

> Harness Engineering（驾驭工程）是围绕 AI 智能体设计和构建**约束机制、反馈回路、工作流控制和持续改进循环**的系统工程实践。

- Prompt Engineering —— 对马喊话的技巧
- Context Engineering —— 给马看的地图
- Harness Engineering —— 给马造一条高速公路，配上护栏、限速牌和加油站

## 驾驭工程的四大护栏
- 护栏一：上下文工程（Context Engineering）——新员工手册

- 护栏二：架构约束（Architecture Constraints）——缰绳
OpenAI 团队建立了严格的层级依赖模型：
**Types → Config → Repo → Service → Runtime → UI**

- 护栏三：反馈循环（Feedback Loop）——智能体审智能体
反馈循环中的钩子可以运行预定义的测试套件，并在失败时带着错误信息循环回到模型，或者提示模型独立评估其代码。如果 AI 写的测试用例通过了带有 Bug 的代码，Harness 就会判定测试无效，强迫它重新思考测试边界。

- 护栏四：熵管理（Entropy Management）——垃圾回收

---

> Birgitta Böckeler 的总结最为精辟：为了获得更高的 AI 自主性，运行时必须受到更严格的约束。增加信任需要的不是更多自由，而是更多限制。就像高速公路上的护栏——正是因为有护栏，你才敢踩到 120 码。

| 核心组件 | 解决的问题 | 代表实践 |
|---|---|---|
| 上下文工程 Context | Agent 不知道该看什么、怎么找 | AGENTS.md 活文档、按需检索 |
| 架构约束 Constraints | Agent 复制并放大坏模式 | 分层依赖、自定义 Linter、CI 强制阻断 |
| 反馈循环 Feedback | Agent 不知道自己做错了 | Agent-to-Agent Review、自动测试套件 |
| 熵管理 Entropy | 技术债务和文档腐烂 | Doc-gardening Agent、持续垃圾回收 |

# Loop Engineering（循环工程） 

```
Prompt：怎么问 AI
↓
Context：给 AI 什么信息
↓
Harness：如何组织 AI 的能力
↓
Loop：如何让 AI 持续创造结果
```

| 工程阶段 | 核心思想 | 关注点 | 输入内容 | AI 能力 | 人的角色 | 典型场景 |
|---|---|---|---|---|---|---|
| Prompt Engineering（提示词工程） | 通过设计提示词获得更好的输出 | 怎么问问题 | Prompt / 指令 | 单轮生成 | 提问者 | 聊天、写作、代码生成 |
| Context Engineering（上下文工程） | 组织并提供完整背景信息 | 给 AI 什么信息 | 知识库、历史记录、约束条件、上下文 | 上下文理解 | 信息组织者 | RAG、AI 搜索、代码助手 |
| Harness Engineering（编排工程） | 连接模型、工具、数据形成工作流 | 如何调用能力 | 上下文 + API + 工具链 | 执行任务 | 系统设计者 | Agent、自动化流程、多工具协同 |
| Loop Engineering（循环工程） | 构建目标驱动的自主闭环系统 | 如何持续完成目标 | 目标、状态、记忆、验证机制 | 规划 → 执行 → 验证 → 修复 → 持续运行 | 规则制定者 | Claude Code、AI 编程、自动运营、AI 员工 |

## 什么是 Loop（循环）
Loop Engineering 是把你从"提示 Agent 的人"变成"设计提示 Agent 的系统"的工程师。

一个 Loop 是一个递归目标系统：你定义一个目的，Agent 不断迭代，直到工作真正完成。

---

## Loop 的核心循环
| 阶段 | 英文名 | 做什么 | 典型信号来源 |
|---|---|---|---|
| 意图 | Intent | 定义目标结果：成功是什么样子，约束是什么 | 开发者或外部系统（Issue、CI 报告） |
| 上下文 | Context | 收集相关代码、文档、报错日志、约定规范 | 代码库、测试输出、历史对话 |
| 行动 | Action | 编辑文件、运行命令、调用工具、草拟方案 | Agent 自主执行 |
| 观察 | Observation | 获取测试结果、编译错误、运行时输出、代码 Diff | 测试框架、类型检查、CI、人工 Review |
| 调整 | Adjustment | 根据观察更新计划，重复循环直到任务完成或被阻塞 | 下一轮内循环 |

## 六大构成要素
一个能够真正独立运行的 Loop 需要五个核心组件，加上一个贯穿始终的记忆系统，缺一不可。

### 要素一：自动触发器（Automations）
在 Claude Code 中，使用 /loop 命令创建定时触发的 Loop：
```md
# 每天工作日早上 9 点运行：读取前一天的 CI 失败和 Issue，
# 将发现写入 TODO.md，并为标记为 quick-win 的问题起草修复方案
/loop "Read yesterday's CI failures and open issues, write findings \
       to TODO.md, and draft fixes for anything labeled quick-win" \
       --schedule "0 9 * * 1-5"

# /goal：运行直到一个可验证的条件成立
# 下面的命令会持续执行，直到认证模块的所有测试通过且 lint 干净
/goal "All tests in test/auth pass and lint is clean"
```

---

### 要素二：并行隔离（Worktrees）
Git Worktree 是解决方案：为每个 Agent 提供独立的工作目录，各自在独立的分支上操作，共享同一个 Git 历史，但文件改动完全隔离。
```md
# 手动创建 worktree（Claude Code 和 Codex 都支持自动管理）
git worktree add ../agent-fix-auth feature/fix-auth-tests
git worktree add ../agent-upgrade-deps feature/upgrade-axios

# 在 Claude Code 中，为子 Agent 配置 worktree 隔离
# 在 .claude/agents/reviewer.md 的 frontmatter 中添加：
# isolation: worktree   → 每个 Agent 获得独立的检出，完成后自动清理
```

---

### 要素三：技能文件（Skills）
Skills（技能文件）解决的是一个每次都在浪费的成本：**每次新对话，Agent 都要从零推断你的项目规范。**

```md
<!-- 文件路径：.claude/skills/project-conventions/SKILL.md -->
---
name: project-conventions
description: 项目编码规范和构建步骤。凡是涉及代码修改的任务都应加载此技能。
---

## 技术栈
- 后端：Node.js 20 + TypeScript 5.4 + Fastify
- 数据库：PostgreSQL 16，ORM 使用 Drizzle
- 测试：Vitest，测试文件放在 src/ 同级的 __tests__/ 下

## 构建命令
- 安装依赖：pnpm install
- 运行测试：pnpm test
- 类型检查：pnpm typecheck
- 构建产物：pnpm build

## 核心约定
- 所有数据库查询必须经过 src/db/queries/ 中的封装函数，禁止在业务层直接写 SQL
- 错误统一使用 AppError 类（src/errors/AppError.ts），禁止 throw 裸字符串
- API 路由文件命名：{resource}.routes.ts，放在 src/routes/
- 新增 API 必须同时更新 docs/api.md

## 禁止事项
- 不得直接修改 migrations/ 目录下的历史迁移文件
- 不得在 .env 文件中提交真实密钥，使用 .env.example 占位
```

一个只能看到本地文件系统的 Loop 能做的事情非常有限。连接器（基于 MCP——模型上下文协议）让 Agent 能够读取 Issue 追踪、查询数据库、调用 API、在 Slack 发消息。

### 要素五：子 Agent（Sub-Agents）
Loop 中最重要的架构决策之一：**把写代码的 Agent 和检查代码的 Agent 分开。**

这种"制作者-检查者"（Maker-Checker）模式也被应用到了 Loop 的停止条件上：Claude Code 的 /goal 命令在每次迭代后，会用一个单独的模型来判断是否"完成"，而不是让做了工作的那个模型来判断。

```md
<!-- 文件路径：.claude/agents/spec-reviewer.md -->
---
name: spec-reviewer
description: 对完成的代码变更进行对抗性审查，验证其符合规范和测试要求。
model: opus            # 使用更强的模型作为验证者
isolation: worktree    # 独立检出，避免污染制作者的工作区
---

你是一个对抗性代码审查员。你的工作不是认可，而是质疑。

收到一个 diff 后，你需要：
1. 运行完整测试套件（pnpm test），记录失败项
2. 运行类型检查（pnpm typecheck）
3. 对照 SKILL.md 中的项目规范检查 diff
4. 验证用户可见的行为变化是否符合原始需求

只有当所有测试通过、类型检查干净、规范无违反时，才输出 APPROVED。
否则输出具体的拒绝理由，不要给出模糊评价。
```
---

### 要素六：持久记忆（Memory）
**把状态写在文件里，文件放在仓库里**。仓库记得，即使模型不记得。

# cron

### 1. 标准 5 字段 cron

格式：

```text
分钟 小时 日 月 星期
*    *    *  *  *
```

| 字段 | 取值范围 | 说明 |
|---|---|---|
| 分钟 | 0–59 | 第几分钟 |
| 小时 | 0–23 | 第几点 |
| 日 | 1–31 | 每月第几天 |
| 月 | 1–12 或 JAN–DEC | 月份 |
| 星期 | 0–7 或 SUN–SAT | 0 和 7 通常都表示周日 |

示例：

| 表达式 | 含义 |
|---|---|
| `0 9 * * 1-5` | 周一到周五每天 9:00 |
| `*/5 * * * *` | 每 5 分钟一次 |
| `0 0 * * *` | 每天 0:00 |
| `0 12 1 * *` | 每月 1 日 12:00 |
| `30 8 * * 1` | 每周一 8:30 |
| `0 0 1 1 *` | 每年 1 月 1 日 0:00 |
| `0 9,18 * * *` | 每天 9:00 和 18:00 |
| `0 9-18 * * *` | 每天 9 点到 18 点整点每小时一次 |

### 2. 常用特殊字符

| 字符 | 含义 | 示例 |
|---|---|---|
| `*` | 任意值/每 | `* * * * *` 每分钟 |
| `,` | 列表 | `0 9,12,18 * * *` |
| `-` | 范围 | `0 9-18 * * *` |
| `/` | 步长 | `*/10 * * * *` 每 10 分钟 |
| `?` | 不指定，常用于 Quartz 的“日/星期”字段 | `0 0 12 ? * MON-FRI` |
| `L` | Last，最后一天/最后一个星期几 | `0 0 L * *` |
| `W` | 最近工作日 | `0 0 15W * *` |
| `#` | 第几个星期几 | `0 0 * * 1#2` 每月第二个周一 |

# uv 比 pip 块的原因

uv 的“快”是一个系统工程的结果。它首先通过拥抱新标准、舍弃旧包袱来简化问题，然后通过并行化、全局缓存和智能的元数据获取等策略来优化执行路径，最后用 Rust 语言将这些设计的潜力充分发挥出来。

- **拥抱新标准，跳过代码执行**：uv 充分利用了近年来的 Python 打包标准（如 PEP 658），可以直接从包索引获取依赖元数据，无需下载完整的包，更不用像 pip 有时必须执行 setup.py 来解析依赖。这从根本上避免了“下载-执行-失败-重试”的缓慢循环。

- **全局缓存与硬链接**：pip 倾向于将包复制到每个虚拟环境中。uv 则维护一个全局的、内容寻址的缓存。当新项目需要某个包时，如果全局缓存中已有，uv 会通过硬链接（Hardlink）或写时复制（Copy-on-Write）直接“引用”该文件，而不是复制整个包。

# 工具调用（Function Calling）

## 工具定义与描述编写
要让 LLM 正确使用工具，首先需要清晰地定义工具，好的工具定义应该像一份清晰的说明书，让 LLM 明白：

- 这个工具是做什么的？
- 什么时候使用它？
- 需要什么参数？
- 参数是什么格式？

```python
# 工具定义示例结构
weather_tool = {
    "name": "get_weather",  # 工具名称
    "description": "获取指定城市的天气信息",  # 工具描述
    "parameters": {  # 参数定义
        "type": "object",
        "properties": {
            "city": {
                "type": "string",
                "description": "城市名称，如'北京'、'上海'"
            },
            "date": {
                "type": "string",
                "description": "日期，格式'YYYY-MM-DD'，或'今天'、'明天'",
                "enum": ["今天", "明天", "后天"]
            }
        },
        "required": ["city"]  # 必填参数
    }
}
```

# Python 实现推理与规划
[Python 实现推理与规划 - 菜鸟教程](https://www.runoob.com/ai-agent/python-reasoning-planning.html)

AI Agent 的推理与规划核心能力。
- ReAct 框架通过推理与行动的循环，让 Agent 能够边执行边调整策略。

- 思维链（CoT） 通过展示逐步推理过程，提升复杂任务的执行准确性。

- 思维树（ToT） 扩展了思维链，支持多路径探索和回溯。

- MCTS 是一种启发式搜索算法，适合复杂决策和规划问题。

- Reflexion 赋予 Agent 自我反思能力，从失败中学习和改进。

- 任务分解策略 是规划能力的基础，包括递归分解、平行分解和层次分解。

- Plan-and-Execute 采用先规划后执行的模式，适合结构稳定的任务。

# 运营与营销的区别？
运营和营销经常被混用，但核心区别可以概括为：

**营销更偏“让用户来、让用户买、让品牌被看见”；**关注获客逻辑，对外。
**运营更偏“让用户留下来、活跃起来、持续转化，并让业务运转更高效”。**关注留存复购，对内。

## 1. 核心目标不同
- **营销**：解决“获客和认知”问题。让目标用户知道产品、产生兴趣、形成购买/使用意愿。关注品牌认知、曝光、线索、获客成本、转化率、市场份额等。
- **运营**：解决“留存和效率”问题。让已有用户更好地使用产品、持续活跃、复购/续费、传播，并优化业务流程。关注留存率、活跃度、复购率、用户生命周期价值、转化漏斗、运营效率等。

## 2. 工作对象不同
- **营销**：更对外，面向潜在用户、市场、渠道、媒体、合作伙伴。做市场调研、品牌定位、内容传播、广告投放、公关、活动推广、渠道合作等。
- **运营**：更对内和对现有用户，面向产品、用户、内容、活动、社群、数据、流程。做用户分层、新手引导、社群运营、活动运营、内容运营、产品运营、数据分析、流程优化等。

## 3. 时间属性不同
- **营销**：常是项目制、 campaign 制，有明确传播周期和获客目标。
- **运营**：常是日常性、持续性工作，强调长期用户关系和数据迭代。

## 4. 典型指标不同
| 维度 | 营销 | 运营 |
|---|---|---|
| 重点 | 拉新、品牌、传播、获客 | 留存、活跃、转化、复购、效率 |
| 指标 | 曝光量、点击率、获客成本、线索量、品牌搜索量 | 留存率、活跃率、复购率、LTV、转化漏斗、用户满意度 |
| 动作 | 定位、传播、投放、渠道、公关、推广活动 | 用户分层、社群、活动、内容、产品优化、数据复盘 |

懂市场的人，谈的是**具体的钱怎么流动**。
不懂的人，谈的是抽象的趋势怎么发展。

# 判断一个人是否懂市场？
市场至少分投资市场、消费市场、B2B市场、交易市场等，先界定语境再判断。

看四个核心能力：
- 能否定义市场
说清楚：客户是谁、在什么场景下、为什么买、替代方案是什么、谁不买。
- 能否拆解供需与竞争
说清楚：供给端谁在卖、成本结构如何；需求端是刚需还是可选；替代品是谁；竞争格局是分散还是集中；进入壁垒和监管是什么。
- 能否用证据而非观点
懂的人会引用一手信息：客户访谈、成交/流失数据、渠道成本、价格测试、竞品定价、复购率、留存、转化率。
- 能否处理不确定性和风险
会讲清：关键假设、验证成本、最坏情况、退出条件。
